# Чому прогін з відмовою не використовує `--rdzv-backend=static`

Відтворення 21.11.2026 тієї самої конфігурації кроку 5, але зі статичним бекендом
рандеву, як у прикладі умови:

```powershell
python -m scripts.lab6_torchrun --nnodes=1 --nproc_per_node=2 --max-restarts=1 --rdzv-backend=static --master-addr=127.0.0.1 --master-port=29500 --node-rank=0 --tee=3 -m lab6.train --task train --sync ddp --global-batch 96 --epochs 1 --ckpt-dir results/lab6/static_rdzv --ckpt-interval 15 --fail-step 37
```

Що сталося (за `events-rank*.jsonl` і `torchrun.log`):

| Час | Подія |
|---|---|
| 14:12:44 | обидва процеси почали навчання |
| 14:12:45 | контрольні точки на кроках 15 і 30 |
| 14:12:46 | процес rank 1 завершився викликом `os._exit(1)` на початку кроку 37 |
| 14:13:46 | агент зупинив групу і запустив обидва процеси повторно |
| 14:14:02 | останній запис у журналі: обидва процеси в `init_process_group` |
| далі | жодної події; через ~8 хвилин процеси зупинені вручну |

Відновлення не почалося: у журналах подій немає ні запису `resume`, ні `start` другої
спроби, тобто перезапущені процеси не вийшли зі створення групи. Той самий сценарій з
`--rdzv-backend=c10d --rdzv-endpoint=127.0.0.1:29500` (адреса і порт так само статичні)
відпрацьовує повністю — `results/lab6/s5_failure/`.

Причину до кінця не встановлено: `StaticTCPRendezvous.next_rendezvous` на перезапуску
створює `TCPStore` на тому самому порту вдруге, поки живий store першої спроби, і це
найімовірніше місце, але доказу (стеку зависання) немає — процеси довелось зупиняти
ззовні. Для роботи це не важливо: `c10d` із фіксованою адресою дає ту саму поведінку, яку
вимагає умова, і решта прогонів ЛР6 статичного бекенда не потребує.

Файл `ckpt.pt` з цієї папки вилучено (контрольні точки не входять у git, див.
`.gitignore`).
